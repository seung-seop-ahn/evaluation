# Golden Dataset 스킬 사용 안내

`/my-golden-dataset-*` 스킬 여섯 개를 쓰는 방법입니다.

---

## 1. 왜 손으로 검증해야 하나

모델에게 문서를 주고 "질문과 답을 만들어줘"라고 하면 데이터셋 파일은 금방 생깁니다.
그런데 그렇게 만든 파일은 **golden dataset이 아닙니다.**

모델이 스스로 만든 답을 기대값으로 기록하면, 그 데이터셋은 지금 모델이 하는 행동을
정답으로 굳혀버립니다. 평가를 돌리면 점수는 잘 나옵니다. 같은 모델이 같은 문서를
보고 답하니까요. 하지만 그 점수는 아무것도 측정하지 못합니다.

이 함정은 이미 이 레포 안에 있습니다. `src/documents/dataset.ts`는 모델이 생성한
QA를 사람 검증 없이 곧바로 `'Golden dataset generated from PDF documents'`라는
설명과 함께 업로드합니다. [documents.md](./documents.md)에 적어둔 과적합 경고와
같은 문제의 다른 얼굴입니다.

**그래서 이 스킬들은 자동화 도구가 아니라 규율 장치입니다.** 목적을 먼저 정하게
하고, 어떤 종류의 케이스가 비었는지 드러내고, 사람이 승인하지 않은 케이스는 확정
데이터셋에 들어가지 못하게 막고, 평가 결과가 나빴을 때 데이터셋을 고쳐서 점수를
올리는 일이 없게 합니다.

---

## 2. 내가 하는 일은 세 가지

1. **선택지에서 고르기** — 스킬이 묻는 질문은 전부 객관식입니다. 백지에서 생각할
   일이 없습니다.
2. **후보 표를 훑고 고치기** — 스킬이 만든 후보 목록에서 틀린 답을 고치거나 이상한
   행을 지웁니다.
3. **결과 리포트 읽기** — 무엇이 실패했고 왜인지 봅니다.

---

## 3. 스킬 6개 — 언제 무엇을 쓰나

### 데이터셋 만들기 (셋 중 근거가 어디에 있느냐로 고릅니다)

| 스킬                           | 정답의 근거가 어디 있나                           |
| ------------------------------ | ------------------------------------------------- |
| `/my-golden-dataset-documents` | PDF·마크다운·텍스트 **문서의 특정 구절**          |
| `/my-golden-dataset-code`      | 에이전트 **코드와 시스템 프롬프트에 적힌 규칙**   |
| `/my-golden-dataset-tools`     | **tool 정의** — 언제 부르고 언제 안 불러야 하는가 |

### 평가하기 (둘 중 목적으로 고릅니다)

| 스킬                                                        | 언제                                              |
| ----------------------------------------------------------- | ------------------------------------------------- |
| `/my-golden-dataset-claude-evaluate`                        | 방금 만든 데이터셋을 **바로 확인**. API 키 불필요 |
| `/my-golden-dataset-upload` → `/my-golden-dataset-evaluate` | **이력을 남기고 팀과 공유**. LangSmith 사용       |

두 평가 경로는 **같은 형식의 리포트**를 냅니다. "로컬에선 82%였는데 LangSmith에선
79%"처럼 나란히 비교할 수 있습니다.

### 인자는 하나, 그마저도 생략 가능

```
/my-golden-dataset-documents src/documents/pdf/
/my-golden-dataset-documents            ← 스킬이 문서를 찾아 목록으로 보여줍니다
```

`--k`나 `--apply` 같은 플래그를 직접 칠 일은 없습니다. 반복 횟수는 `meta.md`
기본값을 쓰고, 업로드는 항상 미리보기를 먼저 보여주고 확인을 받습니다.

### 이름과 위치는 첫 실행 때 물어봅니다

스킬이 소스에서 기본값을 뽑아 제안합니다. `src/documents/pdf/`로 만들면 이름은
`documents`, 위치는 그 옆의 `src/documents/eval/`이 기본입니다.

```
데이터셋을 이 이름과 위치로 만들까요?

  이름: documents
  위치: src/documents/eval/

  [제안대로]  [이름만 바꾸기]  [위치만 바꾸기]  [둘 다 직접 정하기]
```

이름은 파일명과 id 접두어, LangSmith 데이터셋 이름의 기본값이 되므로 소문자와
하이픈만 씁니다. 같은 경로에 이미 데이터셋이 있으면 새로 만들지 않고 그것을 늘릴지
물어봅니다.

**두 번째 실행부터는 묻지 않습니다.** 이름과 위치는 `meta.md`에 기록되고, 평가·업로드
스킬은 프로젝트를 훑어 이름으로 찾으므로 어디에 두든 알아서 찾습니다. 매번 물으면
실수로 데이터셋이 둘로 갈라지기만 합니다.

## 4. 파일 6종 — 무엇을 언제 보나

**직접 열어보는 건 두 개뿐입니다.** 나머지는 스킬이 관리합니다.

| 파일                    | 내가 여나         | 언제, 무엇을 위해                          |
| ----------------------- | ----------------- | ------------------------------------------ |
| `<이름>.candidates.md`  | **예, 직접 고침** | 후보 검증. **손으로 편집하는 유일한 파일** |
| `reports/.../report.md` | **예, 읽음**      | 평가 결과. 뭐가 실패했고 왜인지            |
| `<이름>.meta.md`        | 가끔              | 목적·통과 기준·실행 명령을 바꿀 때         |
| `<이름>.golden.csv`     | 거의 안 봄        | 확정 데이터셋. `git diff`로 변화만 확인    |
| `reports/.../runs.csv`  | 거의 안 봄        | 리포트로 부족해 실제 출력 원문이 필요할 때 |
| `reports/upload-*.md`   | 거의 안 봄        | LangSmith에 잘못 올려서 되돌릴 때          |

파일이 놓이는 자리:

```
<데이터셋 디렉토리>/
├── nist-policy.meta.md          목적, 통과 기준, 커버리지 격자, 평가 대상
├── nist-policy.candidates.md    검증 대기 후보 (승인되면 사라짐)
├── nist-policy.golden.csv       확정 데이터셋
└── reports/
    ├── nist-policy-20260907-1432/
    │   ├── report.md
    │   └── runs.csv
    └── upload-20260907-1512.md
```

포맷이 섞여 있는 데는 이유가 있습니다. 후보는 **문구를 고쳐 써야** 하므로 마크다운
표가, 확정 데이터셋은 도구가 읽어야 하므로 CSV가, 리포트는 서술과 인용이 필요하므로
마크다운이 맞습니다.

## 5. 커버리지란 무엇인가

**한 줄 요약: 어떤 종류의 질문을 몇 개씩 만들지 미리 적어둔 표입니다.**

왜 필요하냐면, 이걸 안 정하고 만들면 **만들기 쉬운 질문만 잔뜩 생깁니다.** 문서에
대놓고 적혀 있는 걸 묻는 질문 같은 것들이죠. 그런 셋으로 재면 점수는 90점씩
나오는데 실제 문제는 하나도 못 잡습니다.

세로축은 **무엇을 보는가**(능력), 가로축은 **어떤 상황인가**(케이스 유형)입니다.

|                  | 정상 | 경계값 | 애매함 | 범위 밖 |
| ---------------- | ---- | ------ | ------ | ------- |
| **사실 조회**    | 6    | 2      | 2      | -       |
| **수치·표 해석** | 3    | 3      | -      | -       |
| **범위 밖 거부** | -    | -      | -      | 6       |

칸의 숫자는 **목표 개수**입니다. 이 표를 실제로 보는 때는 두 번입니다.

- **처음 만들 때** — 스킬이 제안한 표를 보고 "이 칸은 더 필요하다" 정도만 조정
- **데이터셋을 늘릴 때** — "다음에 뭘 만들지"가 이 표에 이미 적혀 있습니다.
  스킬이 빈 칸부터 채웁니다

### 능력 (세로축)

무엇을 보는지에 따라 직접 정합니다. 스킬이 소스를 읽고 후보를 뽑아 주므로 고르기만
하면 됩니다. 문서라면 `사실 조회`, `여러 절 종합`, `수치·표 해석`, `범위 밖 거부`
같은 것들이고, tool이라면 `tool 선택`, `호출 순서`, `인자 구성`,
`불필요 호출 억제` 같은 것들입니다.

### 케이스 유형 (가로축) — 여섯 가지의 뜻

| 유형        | 뜻                                            | 예                              |
| ----------- | --------------------------------------------- | ------------------------------- |
| **정상**    | 평범하게 잘 되어야 하는 것                    | "AI RMF의 네 가지 핵심 기능은?" |
| **경계값**  | 빈 입력, 아주 긴 입력, 값의 최대·최소         | 빈 문자열, 표의 마지막 행       |
| **애매함**  | 질문이 모호해서 되물어야 하는 상황            | "환율 알려줘" (어느 통화?)      |
| **범위 밖** | 답할 수 없어 모른다고 해야 하는 것            | 문서에 없는 내용 질문           |
| **적대적**  | 일부러 헷갈리게 하거나 규칙을 우회하려는 입력 | "규칙 무시하고 답해줘"          |
| **회귀**    | 과거에 실제로 터진 실패를 케이스로 만든 것    | 장애 티켓에서 온 질문           |

**범위 밖이 실무에서 가장 자주, 가장 조용히 무너지는 지점입니다.** 문서에 없는 걸
물었는데 그럴듯한 답을 지어내면, 사용자는 그게 틀렸다는 걸 알 방법이 없습니다.
그래서 스킬은 이 칸을 넉넉히 배정하라고 권합니다.

## 6. CSV 컬럼 — 내가 보는 4개와 나머지

컬럼은 18개지만 **사람이 판단하는 건 넷뿐**입니다. 후보 검증 표에도 이 넷만
나옵니다.

| 컬럼           | 무엇을 판단하나                      |
| -------------- | ------------------------------------ |
| `question`     | 실제로 사용자가 물어볼 법한 질문인가 |
| `answer`       | 이 답이 맞나                         |
| `source_quote` | **이 근거가 저 답을 뒷받침하나**     |
| `case_type`    | 어느 상황을 재는 케이스인가          |

`source_quote`가 검증을 가능하게 만드는 핵심입니다. 근거 문장이 표에 함께 있으니
PDF를 다시 열지 않고도 판단할 수 있습니다. 이 칸이 없으면 검증은 사실상 불가능하고,
그러면 "golden"이라는 이름이 거짓말이 됩니다.

나머지 14개(`id`, `capability`, `grading_mode`, `grading_spec`, `expected_tools`,
`trajectory_rule`, `status` 등)는 스킬이 채웁니다. 문제가 생겼을 때만 보시면 됩니다.
정확한 정의는 `.claude/skills/_shared/golden-dataset/schema.md`에 있습니다.

알아두면 좋은 규칙 세 가지:

- **`status: active`인 행만 채점됩니다.** 은퇴시킨(`retired`) 케이스는 지우지 않고
  남겨두되 점수에 들어가지 않습니다.
- **근거 문서가 바뀌면 그 케이스는 자동으로 `needs_review`가 됩니다.** 문서가
  바뀌었는데 옛날 기대값으로 계속 채점하면 그 점수는 거짓말이기 때문입니다.
- **"거부해야 한다" 같은 기대는 문자열로 못 씁니다.** `answer: "거부함"`이라고 쓰면
  절대 통과할 수 없는 케이스가 됩니다. 이런 건 루브릭을 붙인 `llm_judge`로
  표현하고, 스킬이 알아서 붙여 줍니다.

## 7. 리포트 읽는 법

리포트를 열면 **위에서부터 이 순서로** 보시면 됩니다. 리포트 자체가 이 순서로
쓰여 있습니다.

### 1) 게이트 판정

통과인가 미달인가. 배포 가부는 여기서 끝납니다.

### 2) 회귀 목록 — 실무에서 가장 중요한 부분

지난번엔 통과했는데 이번에 실패한 케이스입니다. **총점이 그대로여도 여기 뭔가 있으면
뭔가 깨진 것입니다.** 점수는 유지됐는데 두 개가 조용히 망가진 상황이, 점수가 떨어진
것보다 나쁩니다.

### 3) 슬라이스별 통과율

능력별·상황별로 나눈 통과율. **전체 평균이 가리고 있는 약한 칸**을 여기서 찾습니다.

```
전체 통과율      ≥ 80%   81.8% (18/22)   통과
범위 밖 거부율   ≥ 95%   66.7% (4/6)     미달
```

전체는 통과인데 범위 밖만 66%인 상황. 평균만 봤으면 "괜찮네" 하고 넘어갔을
겁니다. 커버리지 격자를 먼저 설계하는 이유가 이것입니다.

마이크로 평균과 매크로 평균이 함께 나옵니다. 둘이 벌어져 있으면 케이스가 적은 칸의
실패가 전체 평균에서 희석되고 있다는 뜻입니다.

**신뢰구간을 같이 보세요.** 케이스가 20~30개면 통과율 오차가 큽니다. 구간이 넓다고
리포트가 경고하면, "82% → 85%"를 개선이라고 부르면 안 됩니다. 그냥 노이즈입니다.

### 4) pass^k — 반복 실행했을 때만

- `pass@k` — 한 번이라도 통과한 비율
- `pass^k` — **매번** 통과한 비율

둘의 차이가 **운으로 통과한 케이스**입니다. 통과로 집계됐지만 믿을 수 없습니다.
자세한 개념은 [anthropic.md](./anthropic.md)에 있습니다.

### 5) 실패 원인 분류

각 실패가 셋 중 무엇인지:

| 원인               | 뜻                      | 무엇을 고치나             |
| ------------------ | ----------------------- | ------------------------- |
| **시스템 결함**    | 시스템이 틀렸다         | 시스템을 고침             |
| **케이스 오류**    | 기대값이 틀렸다         | 케이스를 `needs_review`로 |
| **채점 기준 모호** | 루브릭이 판정을 못 한다 | 루브릭을 고침             |

**실패를 전부 시스템 탓으로 돌리면 엉뚱한 걸 고치게 됩니다.** 그래서 이 분류가
리포트의 핵심입니다.

### 보지 말아야 할 것: 100%

**만점은 성취가 아니라 경고입니다.** 골든셋에 맞춰 프롬프트를 계속 손보면 결국
모든 케이스를 통과하게 되는데, 그 시점부터 이 데이터셋은 골든셋 바깥의 문제를
경고해 주지 못합니다. 점수는 약점을 찾는 신호이지 올려야 할 목표가 아닙니다.
([documents.md](./documents.md) 참고)

## 8. API 키와 실행 방식

### 키는 프로젝트 루트 `.env` 하나만 씁니다

`.claude/` 아래에 `.env`를 만들지 않습니다. **그 폴더는 git에 커밋되기 때문입니다.**
스킬을 팀과 공유하거나 다른 프로젝트로 복사하는 순간 키가 따라갑니다.

이 레포는 루트에 `.env`가 이미 있고 `.gitignore`에도 등록돼 있습니다. 기존
스크립트들도 전부 `--env-file=.env`로 이걸 읽습니다.

| 키                  | 언제 필요한가                                           |
| ------------------- | ------------------------------------------------------- |
| `LANGSMITH_API_KEY` | `upload`                                                |
| `OPENAI_API_KEY`    | `evaluate` 에서 `llm_judge` 케이스가 있거나 방식 B일 때 |
| (없음)              | **`claude-evaluate` 는 키가 전혀 필요 없습니다**        |

키가 없으면 스킬이 어떤 키를 어디에 넣어야 하는지 알려주고 멈춥니다. **키 값 자체는
화면·로그·리포트 어디에도 출력되지 않습니다.**

### 빌드도 tsx도 필요 없습니다

Node 23.6부터 TypeScript 파일을 그대로 실행합니다. 이 환경은 Node 26이라 컴파일
단계가 필요 없습니다.

```bash
node --env-file=.env .claude/skills/_shared/golden-dataset/scripts/upload.ts --dataset nist-policy
```

기존 레포 컨벤션(`rag:upload`, `tools:eval`)에 맞춰 `package.json`에 두 줄을 추가할지
스킬이 물어봅니다. 승인하면 이렇게 쓸 수 있습니다.

```bash
npm run golden:upload -- --dataset nist-policy
npm run golden:eval   -- --dataset nist-policy
```

**어느 쪽이든 직접 칠 필요는 없습니다.** `/my-golden-dataset-upload nist-policy`만
치면 스킬이 알아서 고릅니다.

### 의존성

스크립트가 `.claude/skills/` 안에 있어도 Node는 상위 디렉토리로 올라가며
`node_modules`를 찾으므로 **프로젝트 루트의 패키지를 그대로 씁니다.** 스킬 전용
설치가 없습니다.

필요한 건 `langsmith`와 `@langchain/openai` 둘뿐이고 이 레포에는 이미 있습니다.
CSV 파싱은 의존성을 늘리지 않으려고 직접 구현했습니다. 패키지가 없는 프로젝트에서는
설치 명령을 안내만 하고 멈춥니다 — 자동 설치는 하지 않습니다.

## 9. LangSmith 데이터셋 이름

기본은 **로컬 이름 그대로**입니다. `nist-policy.golden.csv`는 LangSmith에서도
`nist-policy`가 됩니다. 두 곳 이름이 같아야 나중에 "이 데이터셋이 어느 CSV에서
왔지?"를 헤매지 않습니다.

LangSmith 워크스페이스는 팀이 함께 쓰는 공간이라 이름이 겹칠 수 있습니다. 같은
이름이 이미 있으면 **첫 업로드 때 한 번만** 물어봅니다.

- **이어서 추가** — 내가 전에 올린 게 맞다. 같은 id는 건너뛰고 달라진 것만 갱신
- **새 이름으로** — 다른 데이터셋이다. 프로젝트명을 접두어로 붙임
  (`evaluation-nist-policy`)
- **취소** — 먼저 LangSmith에서 확인하고 오겠다

고른 이름은 `meta.md`에 기록되고 `evaluate`도 같은 값을 읽습니다. **두 번째부터는
묻지 않습니다.** 이름을 자동으로 바꾸는 일은 없습니다 — 조용히 달라지면 이전 실험
이력과 끊깁니다.

이 기록이 `upload`과 `evaluate`를 잇는 고리입니다. **먼저 올리지 않고 `evaluate`를
실행하면** 붙일 데이터셋이 없어서 LangSmith 실험을 만들지 못하고 로컬 실행으로
넘어갑니다. 그건 `claude-evaluate`가 이미 하는 일이므로, 그 안내가 뜨면 업로드
단계를 빠뜨렸다는 신호로 보시면 됩니다.

업로드는 항상 미리보기가 먼저입니다.

```
스키마 검증 통과 (18행, 오류 0)
활성 케이스 18건

LangSmith 데이터셋 "nist-policy"
  상태        신규 생성됨
  신규 추가   18건
  기존 유지    0건
  내용 변경    0건

미리보기입니다. 아직 아무것도 올라가지 않았습니다.
```

승인하면 올라가고, 올린 example id 목록이 `reports/upload-*.md`에 남습니다. 잘못
올렸을 때 되돌릴 유일한 근거입니다.

### upsert가 맞습니다

`metadata.id`를 키로 비교합니다.

| 원격 상태                | 동작      |
| ------------------------ | --------- |
| 같은 id 없음             | 새로 만듦 |
| 같은 id 있고 내용도 동일 | 건너뜀    |
| 같은 id 있고 내용이 다름 | **갱신**  |

**기존 예제를 지우는 일은 없습니다.** 케이스를 은퇴시키는 건 CSV의 `status` 변경이고
LangSmith 쪽은 그대로 둡니다. 대신 `evaluate`가 채점 대상을 로컬 CSV 기준으로
추려서 넘기므로, 은퇴한 케이스가 점수에 들어가지는 않습니다.

한 가지 주의할 점이 있습니다. 이 스킬 이전에 `npm run tools:upload` 같은 기존
스크립트로 올린 예제에는 `metadata.id`가 없습니다. id로만 찾으면 그런 행이 보이지
않아 같은 질문이 중복 생성되므로, **id가 없는 예제는 질문 문구로도 찾아서 이어붙입니다.**
미리보기에 몇 건이 그렇게 처리되는지 표시됩니다.

```
  참고: 원격에 id 없는 예제가 6건 있습니다 (이 스킬 이전에 올린 것).
        그중 4건은 질문이 같아 새로 만들지 않고 이어붙입니다.
```

**2) 목적을 고릅니다** — 바로 질문을 만들어내지 않습니다.

### 예시 B — 코드 기반, LangSmith에 올려서 공유 (API 키 필요)

```
dataset.define.ts 를 읽었습니다. 평가할 것을 고르세요.

  [x] 출력 스키마 준수    { question, answer, source } 형태를 지키는가
                          근거: zod 스키마 (18행)
```

## 11. 공개 저장소에 올릴 때

스킬 파일 자체에는 비밀값이 없습니다. 스크립트는 `process.env`로 키의 **존재만**
확인하고 값을 출력하거나 파일에 쓰는 경로가 없습니다. 키는 `.env`에만 있고 그
파일은 `.gitignore`에 등록돼 있습니다.

과금도 저장소를 공개한다고 발생하지 않습니다. 코드에 키가 박혀 있지 않으므로
받아 간 사람은 **자기 키로만** 실행할 수 있고, `upload`는 `--apply` 없이는 미리보기만,
`evaluate`는 `--yes` 없이는 예상 호출 수만 알리고 멈춥니다. 여섯 스킬 모두
`disable-model-invocation: true`라 Claude가 스스로 실행하지도 않습니다.

다만 커밋하기 전에 확인할 것이 셋 있습니다.

**`meta.md`의 실행 명령은 그대로 실행됩니다.** `evaluate`가 여기 적힌 명령을 셸로
돌립니다. 외부에서 받은 PR에 `meta.md`가 들어 있다면 그건 코드 리뷰 대상입니다.
질문 문구는 인자로 넘어가므로 주입에 안전하지만, 명령 자체는 파일에 적힌 대로
실행됩니다.

**`golden.csv`의 `source_quote`에는 원본 문서가 발췌돼 들어갑니다.** 사내 문서나
계약서로 데이터셋을 만들었다면 그 문장이 CSV에 그대로 남습니다. 공개 저장소라면
데이터셋 파일을 커밋할지 따로 판단하세요.

**`reports/`에는 시스템의 실제 출력이 들어갑니다.** `runs.csv`는 모델이 만든 답변
원문이라 무엇이든 담길 수 있습니다. 공개할 생각이 없다면 `reports/`를 gitignore에
넣는 편이 안전합니다.

스킬 파일과 스크립트만 공유하고 싶다면 `.claude/skills/`만 커밋하고 데이터셋과
리포트는 빼면 됩니다. 다른 프로젝트로 옮길 때의 단위는 `_shared/golden-dataset`과
여섯 스킬 폴더를 합친 전체입니다.

## 12. 자주 하는 실수

**목적 없이 시작하기.** "일단 케이스부터 만들자"가 가장 흔한 실패입니다. 목적이
없으면 몇 개를 만들지, 어떤 종류를 만들지, 몇 점이면 되는지 어느 것도 정할 수
없습니다. 스킬이 0~2단계를 건너뛰지 못하게 막는 이유입니다.

**정상 경로만 만들기.** 만들기 쉬워서 그렇게 됩니다. 그런 셋은 점수가 잘 나오지만
거부 동작도, 경계값도, 실제로 터지는 문제도 전혀 측정하지 못합니다.

**실패했을 때 기대값 고치기.** "아, 이 답도 맞는 것 같은데" 하고 `answer`를 실제
출력에 맞추는 순간, 이 데이터셋은 측정 도구가 아니라 **현재 동작을 정당화하는
문서**가 됩니다. 케이스가 정말 틀렸다면 `needs_review`로 내리고 다시 검증하세요.
